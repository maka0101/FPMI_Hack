# Контракт Backend ↔ ML v1

Backend и CLI используют один клиент. Адрес сервиса задаёт `ML_URL`, в том числе адрес локального SSH-туннеля к VM. Протокол — HTTP и JSON в UTF-8. Каждый процесс ML обслуживает один профиль и один подготовленный индекс.

## Готовность

`GET /healthz` проверяет, что процесс работает. `GET /readyz` отвечает 200 после загрузки индекса, возвращает его фактические `profile_id`, `index_version` и `corpus_sha256`. Хеш SHA-256 вычисляется по байтам файла documents.jsonl. Версия индекса — непустая строка. Перед первым поиском Backend проверяет профиль и хеш, запоминает версию индекса. Встроенный сервис также передаёт `profile_sha256` — хеш полной конфигурации, включая префикс запроса. Если сервис поддерживает это поле, оно должно совпадать во всех последующих проверках готовности и ответах с кандидатами. При смене версии перезапустите backend с выбранным индексом. В режиме BM25 соединение с ML не требуется.

## Кандидаты

`POST /v1/candidates` принимает исходный запрос, ящик, дату отсчёта, календарный фильтр, глубину выдачи от 1 до 1000 и хеш корпуса. Например, для тестового корпуса выполните команду из корня репозитория.

```sh
CORPUS_SHA=$(shasum -a 256 tests/fixtures/documents.jsonl | cut -d' ' -f1)
curl -fsS "${ML_URL:-http://127.0.0.1:8001}/v1/candidates" \
  -H 'Content-Type: application/json' \
  -d "{\"synthetic_user\":\"box-a\",\"query\":\"чек вчера\",\"query_date\":\"2028-10-02\",\"target_day\":\"2028-10-01\",\"limit\":2,\"corpus_sha256\":\"$CORPUS_SHA\"}"
```

Ответ содержит `profile_id`, `index_version`, `candidates` и для встроенного сервиса `profile_sha256`. Например, при найденном письме элемент списка имеет вид `{"doc_id":"receipt-a","score":0.78}`. Значение score — конечное число. Сервис возвращает уникальные идентификаторы по убыванию score, при равенстве — по возрастанию doc_id. Нет совпадений — пустой список. Для другого хеша корпуса ML возвращает 409, для невалидных полей — 422, при неготовом индексе — 503.

Обе стороны ограничивают выдачу указанным ящиком и датой. При известной дате письма она должна быть не позже query_date. Если указан target_day, допускаются только письма с этой датой. Для интервала backend передаёт `target_day: null` и `target_range`, например `{"start":"2028-09-30","end":"2028-10-02"}`. Обе границы включены. Письма без даты доступны только при отсутствии обоих фильтров. Запрос только с датой или пустым текстом открывает список писем в порядке убывания даты, при равенстве — по doc_id.

## Интеграция и ошибки

BM25 использует SQLite FTS5. Encoder использует порядок ML после проверки доступности писем. Hybrid параллельно получает два списка глубины min(1000, max(50, K)) и складывает для каждого письма вес / (60 + позиция) по спискам, где оно встретилось. Профиль harrier270 даёт вес 0,85 списку BM25 и 0,15 списку Harrier. Остальные профили используют равные веса. Позиции начинаются с 1. При равном результате первым идёт меньший doc_id. Backend возвращает до K писем с полями doc_id, subject, day, preview.

Веб-поиск передаёт фактический режим в `X-Search-Mode` (bm25, encoder, hybrid или browse для просмотра), вычисленную дату при наличии в `X-Target-Day`, границы интервала в `X-Target-From` и `X-Target-To`, серверное время в миллисекундах в `Server-Timing: search;dur=...`. Сбой ML или несовместимость индекса дают 503. Только в гибридном веб-демо с явным DEMO_FALLBACK=1 таймаут допускает ответ BM25 с заголовком `X-Search-Mode: bm25-fallback` и записью в журнале. Эксперименты работают в строгом режиме.
