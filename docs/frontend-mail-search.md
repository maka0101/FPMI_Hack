# Поиск письма по воспоминанию

Спецификация фронтенда для хакатона · проект для согласования с бэкендом.

Человек вводит в одну строку всё, что помнит. Если для поиска нужна дата знакомого события, интерфейс помогает узнать письмо об этом событии. Одного выбора письма достаточно для запуска поиска. Исходная фраза остаётся доступной для правки.

## Сценарии и границы MVP

| Что вводит человек | Что происходит после Enter | Что происходит после выбора письма |
|---|---|---|
| «Смета на ремонт» | Обычная выдача в текущем ящике | Открывается выбранная смета |
| «Смета после письма про билеты в Казань» | «После какого письма искать смету?» и до трёх билетов | Сметы за день билета и три следующих дня |
| «Договор до письма с приглашением на встречу» | «До какого письма искать договор?» и кандидаты по приглашению | Договоры за три предыдущих дня и день приглашения |
| «Ищу смету на ремонт. Я примерно тогда покупал билеты в Казань» | «Какое письмо поможет вспомнить дату покупки?» и кандидаты по покупке билетов | Сметы в пределах трёх дней в обе стороны |
| «Письма рядом с покупкой билетов в Казань» | Тот же выбор письма о покупке | Соседние письма по близости дат. Целевой запрос пуст |
| «Ищу адрес конференции, на которую покупал билеты в Казань» | В MVP вся фраза поступает в обычный поиск. Пользователь сразу видит выдачу | Открывается выбранный результат |

**Граница смысловой связи.** В последнем сценарии билеты подсказывают, о какой поездке идёт речь. Дата покупки сама по себе ничего не говорит о дате письма с адресом. Для MVP такой запрос допускает совпадения по словам и смыслу в пределах всего доступного ящика. Выявление связей между разными письмами об одной поездке — отдельное расширение. Для него потребуется ответ сервера с причиной связи, например общим номером брони и фрагментами обоих писем. До согласования такого контракта UI показывает обычные карточки.

## Экран и взаимодействие

- **Вход.** Вверху ящик, дата отсчёта, одна строка и «Найти». При пустой строке виден короткий пример «Ищу смету. Примерно тогда покупал билеты». Пустая отправленная строка по-прежнему открывает последние письма ящика.
- **Выбор ориентира.** В области выдачи сразу появляются вопрос и до трёх кнопок с темой, датой и фрагментом. Отдельного поля отправителя в текущих данных нет. Даже одного кандидата подтверждает человек. Здесь же доступно «Искать всю фразу» для исправления ошибочного разбора.
- **Результаты.** Над списком видны цель, направление, тема выбранного письма и фактические даты окна. Например, «Смета на ремонт · 12–15 мая, после письма “Билеты в Казань”». Тема открывает повторный выбор ориентира. У каждой карточки подпись «В тот же день», «За день до» или «Через 2 дня». В исходных данных точность до дня.
- **Чтение.** На широком экране список слева, текст письма справа. На узком открытое письмо занимает область списка, «К результатам» возвращает прежний список, прокрутку и фокус на выбранную строку.
- **Пустой ответ.** Для ориентиров — «Не нашли письмо о покупке билетов», действия «Изменить запрос» и «Искать всю фразу». Для пустой итоговой выдачи при окне 3 дня — «Расширить до 7 дней». При пустом окне 7 дней — «Сменить письмо» и, если есть цель, «Искать смету во всём ящике». Последнее действие отправляет только цель.
- **Управление.** Enter в строке отправляет запрос. Кандидаты доступны через Tab и стрелки, Enter выбирает письмо, Esc возвращает фокус в строку. После выбора фокус переходит к заголовку выдачи. Загрузка, число результатов и ошибки объявляются через область статуса.

## Ответственность на клиенте

Основа — существующая страница на HTML и JavaScript. Имена в таблице обозначают обязанности, структуру файлов можно выбрать при реализации.

| Часть страницы | Данные и действия |
|---|---|
| Форма и разбор запроса | Хранит редактируемый текст отдельно от отправленного. На Enter возвращает обычный запрос либо цель, описание ориентира и направление |
| Контроллер поиска | Владеет выбранным ящиком, датой, отправленной фразой, разобранным запросом, кандидатами, выбранным ориентиром, размером окна и состоянием текущей операции |
| Клиент почтового API | Формирует параметры и JSON, читает ответы и заголовки, различает пустой ответ, ошибку и отмену. Единственный сетевой адресат браузера — бэкенд приложения |
| Список и панель чтения | Список отображает кандидатов либо результаты в порядке сервера. Панель получает идентификатор письма и ящик с датой именно той выдачи, из которой его открыли |

**Разбор в MVP.** Локальные правила распознают явные обороты «после письма…», «до письма…», «примерно тогда…», «примерно в то же время…» и «письма рядом с…». Примеры из таблицы выше входят в приёмку. В конструкции «Я примерно тогда покупал билеты в Казань» в поиск ориентира уходит «покупал билеты в Казань», цель берётся из первой части. Пустая цель допустима при явном запросе соседних писем. Для неуверенного разбора, нескольких конкурирующих ориентиров или обычного запроса вроде «смета после ремонта» сохраняется поиск по исходной фразе. Прямые вызовы LLM, ML-сервиса или стороннего API для этого потока не требуются.

**Переходы.** Обычная отправка открывает состояние загрузки выдачи. Отправка с временной связью запускает загрузку ориентиров → выбор → загрузку выдачи → результаты или пустое окно. Расширение окна повторяет только последнюю поисковую операцию. Чтение имеет своё состояние загрузки и ошибки. Повтор после сетевой ошибки использует сохранённые параметры упавшей операции.

**Согласованность.** Редактирование меняет черновик. Новый Enter сбрасывает ориентир и окно до 3 дней. Смена ящика или даты закрывает письмо, сбрасывает кандидатов и повторяет последнюю отправленную фразу в новом контексте. Смена ящика также подставляет его дату по умолчанию. Контроллер отменяет предыдущие запросы либо игнорирует ответы с устаревшим номером операции. Это относится и к запоздалому ответу чтения после смены выдачи.

## Контракт браузера с бэкендом

Текущая реализация описана в [API](../mail_search/api.py) и [странице поиска](../mail_search/index.html). Ниже существующие вызовы и два предложения для согласования. Все даты — календарные строки YYYY-MM-DD. Идентификаторы писем и ящиков браузер трактует как непрозрачные строки.

| Событие | Запрос | Ответ |
|---|---|---|
| Открытие страницы · существует | GET /api/mailboxes | Объект, где ключ — ящик, значение — его дата по умолчанию или null. При null UI использует текущую дату |
| Обычный поиск · существует | GET /api/search с mailbox, as_of, q. Пустой q означает просмотр последних писем | Массив карточек doc_id, subject, day, preview. day может быть null. Сохраняется поддержка X-Target-Day и X-Search-Mode |
| Поиск ориентиров · расширение существующего вызова | GET /api/search с теми же mailbox, as_of, с q из описания события, limit=3 и новым dated_only=true | До трёх карточек с известной датой. Для обычного поиска значение dated_only по умолчанию false. Сервер применяет это условие до отсечения кандидатов |
| Выбор ориентира или расширение окна · новый вызов | POST /api/search/nearby с JSON по примеру ниже | Фактические границы окна и упорядоченные карточки с разницей в днях |
| Открытие конкретного результата · существует | GET /api/message с mailbox, as_of, doc_id | doc_id, subject, day, body. Интерфейс выводит текст письма |

Пример предложенного запроса после выбора билета. При расширении меняется только window_days.

```json
{
  "mailbox": "box-a",
  "as_of": "2026-05-14",
  "q": "смета на ремонт",
  "anchor_doc_id": "ticket-12",
  "direction": "after",
  "window_days": 3,
  "limit": 10
}
```

Пример ответа для билета от 12 мая. Верхняя граница учитывает выбранную дату отсчёта.

```json
{
  "window": { "from": "2026-05-12", "to": "2026-05-14" },
  "results": [
    {
      "doc_id": "estimate-14",
      "subject": "Смета на ремонт ванной",
      "day": "2026-05-14",
      "preview": "Отправляю расчёт по материалам.",
      "delta_days": 2
    }
  ]
}
```

- Для nearby все поля примера обязательны. q — строка, включая пустую для просмотра соседних писем. direction принимает before, after или around. window_days принимает 3 или 7. limit — целое от 1 до 10, клиент запрашивает 10.
- Обе границы окна включительны. Для дня ориентира D и размера N интервалы равны [D−N, D], [D, D+N] и [D−N, D+N] соответственно. Верхняя граница всегда ограничена as_of. Сервер получает дату ориентира по anchor_doc_id и проверяет доступность в текущем ящике. Из кандидатов исключаются сам ориентир и письма без даты.
- Бэкенд применяет ящик и окно **до отбора топ-10**. Для заполненной цели порядок определяется релевантностью, затем близостью даты. Для пустой цели — по возрастанию абсолютного delta_days. При равенстве используется doc_id. delta_days равен дню результата минус день ориентира. Браузер сохраняет порядок ответа.
- Пустой результат — HTTP 200 с пустым массивом в соответствующем формате. Для nearby предлагаются 400 при некорректных параметрах или отсутствии даты у ориентира, 404 при недоступном ориентире, 503 при недоступном поиске. Ошибки содержат поле error. При 404 интерфейс предлагает выбрать ориентир заново, при 400 — исправить условие, при 503 или сетевой ошибке — повторить. Ошибка открытия письма показывается внутри панели чтения.
- Текст письма запрашивается только при открытии. Ящик и as_of сопровождают оба этапа поиска и чтение. Координация с ML, включая поддержку поиска внутри окна, находится за почтовым API. Владельцы бэкенда и ML согласуют её между собой по [действующему внутреннему контракту](contracts/ml-search-v1.md).

## Порядок работы и приёмка

| Этап | Результат будущей работы | Зависимость |
|---|---|---|
| 1. Согласовать границу API | Фронтенд и бэкенд фиксируют dated_only, nearby, формат ошибок и правила дат. Для демо выбирают один ящик с узнаваемым ориентиром и несколькими похожими целями | [Формат корпуса](../mipt_mail_search_participants/README.md) и пример обмена выше |
| 2. Собрать поток на локальных ответах | Одна форма, разбор сценариев, выбор, итоговый список, чтение, смена ориентира, расширение окна. Все развилки можно проверить на фиксированных карточках | Согласованные формы запросов и ответов |
| 3. Подключить API | Обычный поиск и чтение используют существующие операции. Контекстный поиск использует согласованные расширения | Доступны новые возможности почтового API |
| 4. Пройти сквозную приёмку | Проверить сценарии из первой таблицы и границы ниже на широком и узком экранах | Подключённый API и выбранный ящик |

**Проверяемые условия**

1. В каждом временном сценарии человек вводит одну фразу и выбирает ориентир одним действием. До выбора UI показывает кандидатов. После выбора открывается целевая выдача.
2. При «примерно тогда» находятся подходящие письма с обеих сторон ориентира. При «до» и «после» — с соответствующей стороны, включая тот же день. Будущие и чужие письма исключены.
3. В тестовом наборе нужная смета за пределами общего топ-10 попадает в топ-10 внутри окна. Письма без даты не вытесняют датированные ориентиры из тройки.
4. Для пустого окна действие «Расширить до 7 дней» сохраняет цель, ящик, дату, направление и выбранный doc_id. Для пустой цели соседние письма упорядочены по расстоянию в днях.
5. Запрос про адрес конференции сразу отправляет исходную фразу в обычный поиск. Временной фильтр появляется только при распознанной временной связи и выборе ориентира.
6. После смены ящика запоздалый ответ поиска или чтения из прежнего ящика не появляется. Сетевую ошибку можно повторить с прежними параметрами. Пустой результат, недоступный ориентир и ошибка сервиса имеют разные действия восстановления.
7. С клавиатуры можно выбрать ориентир, открыть смету и вернуться в ту же выдачу. На узком экране читаются и выбранное условие, и подписи относительных дат.
