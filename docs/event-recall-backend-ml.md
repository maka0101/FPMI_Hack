# «Вспомнить по событию» · бэкенд и ML

Проект контракта для [нижней панели и экрана хронологии](event-recall-frontend.md). Обычный поиск, получение ящиков и чтение письма уже есть в [почтовом API](../mail_search/api.py). Следующие операции предлагаются для нового функционала.

| Операция | Что получает бэкенд | Что возвращает фронту |
|---|---|---|
| Подобрать период по подсказке | Ящик, дата отсчёта, текст воспоминания | В зависимости от подсказки возвращает до трёх датированных ориентиров с направлением, готовый диапазон дат или просьбу уточнить дату либо описание. Ноль кандидатов — допустимый результат. |
| Подтвердить границы для предпросмотра | Ящик, дата отсчёта и либо идентификатор выбранного ориентира, направление и ширина окна, либо явно заданные даты | Фактические включительные границы, доступные на дату отсчёта, и сведения об ориентире при его наличии. Эти условия передаются в оба следующих действия. |
| Уточнить поиск | Тот же контекст и условия периода, исходный поисковый запрос | До десяти ранжированных карточек, применённые границы и, при наличии ориентира, разница дат в днях. |
| Получить хронологию | Ящик, дата отсчёта, границы просматриваемого интервала, необязательный ориентир и курсор продолжения | Карточки по возрастанию даты, курсор следующей страницы и фактические границы. UI группирует письма по дням. Полный текст открывается существующим вызовом чтения. |

**Бэкенд.** Даты определяются правилами относительно выбранного `as_of`. Для явно указанного закрытого периода сохраняются обе границы. Для одного дня D режим «примерно тогда» даёт D ± 3 дня. Для «до» и «после» окно включает сам день D и три дня с соответствующей стороны. Расширение меняет 3 на 7. Для однозначного периода A–B выражение «после периода» начинает окно со следующего дня после B, «до периода» заканчивает его накануне A. Неоднозначные праздники и периоды требуют уточнения. Предпросмотр и выдача используют один расчёт. Если весь интервал в будущем, UI получает просьбу изменить даты.

**Отбор писем.** Сервер проверяет принадлежность ориентира ящику и получает его дату из индекса. Границы ящика, даты отсчёта и окна применяются во всех ветках поиска до отбора топ-K. Письма с неизвестной датой пропускаются. Уточнённый поиск исключает ориентир, при равной релевантности предпочитает ближайшую дату. Хронология включает ориентир отдельной обычной карточкой, если тот попадает в интервал. Для стабильной пагинации порядок задаёт пара `(day, doc_id)`. Переход к соседней неделе начинается сразу за границей текущего интервала.

**ML.** Существующий гибрид BM25 и эмбеддингов подходит для двух задач — распознать знакомое письмо по описанию события и ранжировать целевые письма в выбранном окне. Внутреннему контракту поиска нужны ограничение «только датированные» для ориентиров и диапазон дат для уточнённой выдачи. Сегодня он описывает одну целевую дату. Хронологию бэкенд выбирает напрямую из индекса. Для MVP разбор явных дат и направлений выполняется правилами. [Текущий контракт Backend ↔ ML](contracts/ml-search-v1.md)

**Совместная проверка.** На одном размеченном примере команда проверяет попадание ориентира в первую тройку и цели в топ-10 внутри окна. Отдельно проверяет, что хронология показывает все доступные письма интервала, включая ориентир, и что на границе страниц нет пропусков и повторов.

## Контракт клиента v2

Клиент отправляет POST на маршруты ниже. В каждом JSON-запросе есть `mailbox` и `as_of`. Даты передаются в формате YYYY-MM-DD. Карточка использует имеющиеся поля `doc_id`, `day`, `subject`, `preview`.

| Маршрут | Дополнительные поля запроса | Ответ |
|---|---|---|
| `/api/event-recall/suggest` | `text` | `{kind: "anchors", direction, candidates}`, `{kind: "period", from, to}` или `{kind: "clarify", message}` |
| `/api/event-recall/period` | `from, to` либо `anchor_doc_id, direction, window_days` | `{from, to}` после проверки и ограничения по `as_of` |
| `/api/event-recall/search` | Те же поля периода и `q, limit` | `{window: {from, to}, results}`. Для ориентира карточка включает `delta_days` |
| `/api/event-recall/timeline` | `from, to, cursor, limit` и при наличии `anchor_doc_id`. Первый запрос передаёт `cursor: null` | `{results, next_cursor}`. После последней страницы `next_cursor: null` |

Направление принимает `before`, `after` или `around`. Для пустой выдачи сервер возвращает пустой массив. Ошибки могут передавать текст в поле `error`.
