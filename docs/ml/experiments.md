# Сравнение поиска на одном корпусе

## Публичный dev

Из корня репозитория выполните команды ниже. Первая готовит зависимости из lock-файла. Вторая строит индексы. Третья запускает один BM25 и по два варианта выдачи для каждого профиля (encoder и hybrid). Все пять прогонов используют один набор ящиков, дат, запросов и общее K.

```sh
uv sync --locked --python 3.11
source .venv/bin/activate
python -m mail_search prepare --profiles encoder-a,encoder-b
python -m mail_search compare --profiles encoder-a,encoder-b --limit 10 --out runs/dev
```

Для другого корпуса поставьте `--data /путь/к/каталогу` **перед** именем команды или задайте `DATA_DIR`. Для отдельного Compose-проекта используйте разовый контейнер. Индексы в контейнере доступны через `ARTIFACT_DIR`, отчёты сохраняются на хосте в `./runs`.

```sh
docker compose -p mail-experiment run --build --rm --no-deps ml \
  python -m mail_search compare --profiles encoder-a,encoder-b --limit 10 --out runs/compose-dev
```

Внутри `compare` каждый профиль проходит подготовку или проверку кэша. Затем команда запускает собственный процесс ML на свободном порту loopback, сверяет готовность, профиль, версию индекса и хеш корпуса. После encoder и hybrid процесс завершается. Сбой подготовки, недоступная модель или несовпадение индекса прерывают сравнение с ошибкой. Итоговый каталог появляется после успешного завершения всех вариантов.

## Как читать отчёт

| Артефакт в каталоге прогона | Содержание |
|---|---|
| `report.json` | Конфигурации профилей и ревизии, хеши входов и исходников Python, версия кода, системная информация, K, число запросов, таймаут ML, агрегаты для каждого варианта |
| `bm25/rankings.jsonl` | Один BM25 baseline для всех сравнений |
| `<профиль>/<режим>/rankings.jsonl` | По одной записи с `query_id` и уникальными `doc_ids` в порядке выдачи |
| `<профиль>/<режим>/deltas.jsonl` | На каждом запросе изменение Recall, nDCG, MRR и позиции изменившихся писем. `null` у ранга означает отсутствие в соответствующем топ-K |

В `runs` отчёта `metrics.recall` показывает среднюю долю найденных релевантных писем. Для `ndcg` используется выигрыш 2^relevance − 1 и скидка 1/log₂(позиция + 1). `mrr` учитывает первое релевантное письмо по всем запросам с положительной разметкой. Отдельное поле `mrr_single_hit` сохраняет сопоставимость с историческим baseline на запросах с одним релевантным письмом. Пустая выдача размеченного запроса получает нули. Знаменатели указаны в `judged_queries` и `single_hit_queries`. В `vs_bm25` приведены числа улучшений, регрессий и равенств для каждой метрики.

В `models` указаны время подготовки или использования готового индекса (`prepare_ms`) и время запуска процесса ML до готовности (`ml_ready_ms`). В `runs.*.search_ms` лежат p50, p95 и p99 последовательных вызовов общего движка. Для вывода о задержке веб-сервиса нужен отдельный HTTP-прогон.

Чтобы повторить эксперимент, используйте те же входные файлы, ревизию кода, lock-файл, профили и K. Укажите новый каталог, например `--out runs/dev-repeat`. Сверьте хеши в двух `report.json`, затем позиции в JSONL. Время может отличаться. Рабочие каталоги сборки, процессы и кэш ОС влияют на измерения.

```sh
diff runs/dev/encoder-b/hybrid/rankings.jsonl runs/dev-repeat/encoder-b/hybrid/rankings.jsonl
```

## Собственные и закрытые запросы

Файл запросов использует схему `query_id, synthetic_user, query, query_date`. У каждой строки должен быть уникальный `query_id`. Для отложенных формулировок задайте отдельные файлы и каталог отчёта. Укажите `--qrels` только для вручную проверенной разметки этого набора.

```sh
python -m mail_search compare --profiles encoder-a,encoder-b --limit 10 \
  --queries heldout/queries.jsonl --qrels heldout/qrels.jsonl --out runs/heldout
```

При явном `--queries` без `--qrels` команда `compare` сравнит ранги, сохранив `metrics: null`. Для финальной выдачи одного режима достаточно `export`. В режиме BM25 локальный сервис ML не нужен. Для encoder и hybrid запустите нужный профиль локально или подключитесь к VM и укажите `ML_URL`.

```sh
ML_URL=http://127.0.0.1:18001 python -m mail_search export --mode hybrid \
  --profile encoder-a --queries private/queries.jsonl --limit 10 --output runs/private/rankings.jsonl
```

Для сравнения отдельного работающего ML с ранее сохранённым baseline используйте `benchmark --mode encoder --profile encoder-a --limit 10 --output runs/encoder.jsonl`. Внешний ML задаётся через `--ml-url` или `ML_URL`. Пример подключения локального интерфейса и CLI к одной VM приведён в [инструкции по инфраструктуре](../infrastructure.md).

## Серверная задержка под нагрузкой

Сначала запустите нужную конфигурацию backend и ML, проверьте `/readyz`. Ниже команда для hybrid. Укажите фактические CPU и RAM сервера в `--hardware`. Если ML работает на другой машине, опишите также её и канал подключения.

```sh
python -m mail_search loadtest --url http://127.0.0.1:8000 --mode hybrid --limit 10 \
  --warmup 99 --requests 990 --concurrency 4 \
  --hardware "CPU и RAM сервера и ML" --output runs/load-hybrid.json
```

Внутренний профиль выполняет 99 запросов прогрева и 990 измеряемых с четырьмя параллельными клиентскими запросами. Обе фазы циклически повторяют строки входного файла с начала. Backend работает непрерывно между фазами, индексы загружены в память. Выражение nearest-rank берёт элемент с позицией ⌈p × N⌉ в отсортированной серии. Источник времени — заголовок `Server-Timing: search;dur=…` от получения запроса в приложении до готовой выдачи, включая серверный вызов ML. Сеть от клиента до backend и отрисовка браузера исключены.

Отчёт сохраняет готовность сервера, введённое описание оборудования, параметры машины-генератора, количество успешных измерений, ошибки прогрева и измерения, p50/p95/p99. Команда возвращает код 0 при p99 строго меньше 1000 мс и успешных ответах в обеих фазах. HTTP-ошибки, fallback, неожиданный режим и отсутствие серверного времени делают прогон неуспешным. Короткий smoke допускает `--warmup 2 --requests 8 --concurrency 2`. Для сравнения профилей повторите полный замер при одинаковой нагрузке на целевой машине.
